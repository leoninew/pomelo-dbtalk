# JSONL 数据库数据传输
最后修改时间: 2026-08-20 15:31:55

Review status: Accepted

Mode: standard

## 迁移说明

本文档的已接受需求现归属 `dbtalk`。其中 JSONL 传输格式、CLI 和通用 skill 的所有权已随能力迁移；上游业务项目只通过 CLI 调用，不构成本项目的领域模型或 Python API。

## Background

`dbtalk` 提供 `mysql dump` / `mysql restore`，它们调用 MySQL 原生工具处理 SQL dump，包含 SQL 文件本身的 DDL/DML 语义。SQLite 与 MySQL 间的数据迁移需要另一项能力：以数据库无关的结构化载体传输表数据，目标库的 schema 仍由其所属应用迁移创建。

通用的导出、JSONL 载体处理、跨 SQLite/MySQL 导入和转换责任由 `dbtalk` 承担；不得将调用方的服务、版本和路由模型带入本项目。

## Goal

1. 在 `dbtalk` 中提供 SQLite 与 MySQL 的全库数据导出和导入能力，使用单个 JSONL 文件作为规范传输载体；与 JSONL 格式有关的文档、转换和 CLI 均归属 `dbtalk`。
2. JSONL 按表块（table block）组织：表块起始记录定义表名、列顺序和主键/联合主键，后续行只承载该表值，避免逐行重复表和主键元数据。
3. 只传输数据，不创建或修改 schema，也不处理索引、视图、触发器、存储过程、权限或其他非数据对象。
4. 导出不区分插入和覆盖；同一 JSONL 文件可用于不同导入策略。
5. 导入提供严格插入与覆盖：插入遇到任意数据库约束冲突时失败；覆盖按目标表主键或联合主键更新已有行并插入新行。覆盖前必须完成目标表主键及 JSONL 主键列预检。
6. 导出和导入均支持重复指定 `--exclude-table`，显式排除指定表；未指定时处理全部表，排除项不存在时失败。
7. JSONL 中的 `DATE`、`TIME` 和日期时间使用标准 ISO 8601 字符串。`DATE`/`TIME` 原样传输；无偏移日期时间通过导出和导入共用的 `--tz <IANA timezone>` 解释，默认 `UTC`。带 `Z` 或显式偏移的值优先按自身偏移处理。
8. 以表块为事务边界：单个表块成功后提交，块内失败回滚。默认不承诺跨表整文件原子性。
9. 将通用数据库传输用法以 dbtalk skill 发布；该 skill 不包含调用方服务闭包的业务选择规则。
10. `database export` 省略 `--output` 时，在当前目录的 `data/` 创建带时间戳的 `<source>-<timestamp>.jsonl`；`--archive` 时使用 `.jsonl.gz`。`--output` 指向已有目录时采用同一命名规则；其他路径视为文件，父目录必须已存在。

## Non-goal

- 不取代已有 `dbtalk mysql dump` / `mysql restore`，也不改变其 SQL dump/restore 语义。
- 不创建数据库、创建表或执行应用迁移；目标应用必须先完成自身的 schema 初始化。
- 不提供 DDL、索引、视图、触发器、存储过程或权限的导入导出。
- 不实现海量数据优化、分片、断点续传、checksum、签名或多文件清单。
- 不实现调用方的服务导出闭包、版本谱系、路由关系或其 skill。
- 不在本需求中决定是否保留单独名为 `convert` 的 CLI；JSONL 是统一载体后，旧 SQL 方言转换没有等价的核心职责。

## User scenarios

1. 管理员从 SQLite 导出一个 JSONL 文件，在目标应用已初始化 schema 的 MySQL 数据库中以插入或覆盖模式导入。
2. 管理员从 MySQL 导出同一格式的 JSONL 文件，导入到兼容 schema 的 SQLite 数据库，无需先渲染 MySQL 或 SQLite SQL 文件。
3. 管理员以插入模式导入：逐行执行普通插入，任意约束冲突都明确失败；无主键表可以插入，但不能使用覆盖模式。
4. 管理员以覆盖模式导入：导入器先验证目标表存在与传输文件一致的主键或联合主键，再更新冲突行并插入新行；任一表块预检失败时不得写入该块。
5. 管理员导出数据库中无时区的日期时间字段，默认将其按 UTC 解释并导出为 UTC ISO 8601；需要源值表示上海本地时间时，传入 `--tz Asia/Shanghai`。导入时也可传入 `--tz` 指明目标库边界的解释时区。
6. 管理员调用 dbtalk 的通用 skill 完成传输；处理调用方的单个服务时，应转而调用其提供的服务级 skill。

## Acceptance

- [ ] dbtalk 提供有文档的 SQLite/MySQL 全库 JSONL 导出、导入入口；该入口与 MySQL 原生 dump/restore 命令并存且职责不重叠。
- [ ] 一个传输文件由有序表块构成；表块头包含表名、列顺序和主键/联合主键信息，后续记录不重复这些元数据。
- [ ] JSONL 可无歧义表达 `NULL`、字符串、数字、布尔值、BLOB、Decimal、`DATE`、`TIME` 和日期时间；BLOB 等非 JSON 原生值使用明确的类型标记。
- [ ] 导入只操作目标 schema 中既存且兼容的表、列；缺表、缺列或类型不兼容时失败，不隐式创建或修正 schema。
- [ ] 插入导入遇到任意数据库约束冲突时失败；覆盖导入按完整主键或联合主键更新和插入，不清空表。
- [ ] 导出和导入支持重复 `--exclude-table`，排除指定表；未提供时处理全部表，未知排除项失败。
- [ ] 覆盖导入在写入前验证目标主键定义、表块主键声明和所有主键列；预检失败时不开始该表块的数据写入。
- [ ] `DATE`/`TIME` 以 ISO 8601 字符串原样传输，不做时区转换；日期时间使用 `--tz <IANA timezone>` 解释无偏移值，默认 `UTC`，显式偏移或 `Z` 优先。
- [ ] 日期时间导出被规范为 UTC ISO 8601；导入默认以 UTC 写入目标库，`--tz` 可覆盖目标数据库边界的解释策略。
- [ ] SQLite 与 MySQL 的导入分别使用正确的驱动、参数绑定、类型适配和表块事务；失败回滚当前表块。SQLite 完成后恢复外键检查并执行完整性检查。
- [ ] 提供 dbtalk usage 文档和 skill，明确目标 schema 前置条件、插入/覆盖语义、`--exclude-table`、`--tz`、表级事务与敏感数据文件风险。
- [ ] 调用方不再维护独立的全库传输实现和通用格式文档；服务级功能改为消费此处确定的稳定能力。
- [ ] `database export` 可省略 `--output`；默认目录不存在时创建。已有目录路径产生带时间戳的 JSONL 制品；非目录路径仅作为文件路径处理，父目录不存在时失败。

## Open questions

- JSONL 的精确记录模型：是否使用 `meta`、`table`、`row`、`end` 等记录类型；表块头是否包含行数或列类型，需要在 Plan 中确定。
- SQLite 中日期时间通常没有类型语义。表块头是否应携带 temporal-column 元数据，或导出器如何可靠识别应规范化的日期时间列，需在 Plan 中确定。
- 表块顺序、跨表外键检查、前序表块已提交后后续失败的报告和恢复策略，需要在 Plan 中确定。
- JSONL 已消除 SQL 方言转换的必要性；是否还需要面向旧传输文件的迁移/转换入口，应在 Plan 中按实际兼容需求决定。
- dbtalk CLI 的命令组名称、连接参数形式，以及是否将 SQLite/MySQL 驱动作为可选依赖，需在 Plan 中结合现有 Click/Dynaconf 约定确定。

## Decisions

- dbtalk 是通用全库数据传输的代码、文档、CLI 和 skill 的唯一所有者；调用方不维护第二套全库实现。
- JSONL 是唯一的规范传输载体；独立 SQL 文件渲染不属于本需求。
- 表块头中的主键信息仅用于数据映射、导入预检和冲突处理，不用于创建或修改 schema。
- 插入是严格普通插入，覆盖是基于主键的更新加插入；两者由导入选项决定，导出文件不携带模式。
- `--exclude-table` 是导出和导入两侧的显式表过滤选项，不改变 JSONL 格式。
- 表级事务是默认边界，不默认承诺整文件原子性。
- `DATE`/`TIME` 不进行时区转换；日期时间默认 UTC，且 `--tz` 是导出与导入共用的显式时区参数。
- 输出路径按存在状态判定：已有目录表示生成目录；其余路径表示文件。该规则不根据后缀、路径文本或末尾分隔符推断目录。

## Risk

- 覆盖导入依赖目标 schema 的准确主键定义；无主键表只能插入。
- 表级提交降低事务规模，但跨表失败可能留下前序已提交表块；使用方必须理解并处理失败报告。
- 只传数据要求源、目标应用保持兼容 schema；同名表不代表业务含义或类型一定兼容。
- 无时区日期时间的实际语义无法从许多 SQLite 数据库自动推断，调用方必须正确设置 `--tz`。
- JSONL 文件包含业务数据，即使 BLOB 等被编码后仍应视为敏感文件。

- 本迁移确认 dbtalk 拥有通用数据库传输的文档、导出、导入、类型转换与 skill；调用方只保留服务级能力。
- 调用方与 dbtalk 使用 CLI 进程边界，而不是跨仓库 Python library API。
- 用户要求进入 Plan / 计划阶段。
